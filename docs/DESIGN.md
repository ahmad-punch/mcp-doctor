# Design

The central decision is that rules run against a **snapshot of raw wire-format JSON**, not against the SDK's typed models or a live session. The probe connects once, follows pagination for every list method, dumps each tool, resource, template, and prompt to a plain dict, and records timings and list failures alongside them; every rule is then a pure function from that snapshot to `(target, message)` pairs, registered with its ID, severity, title, and fix hint in one place. This makes each rule unit-testable with a three-line fixture, keeps `--rules`, `--ignore`, the score, the JSON report, and the README table derived from the same records, and lets the linter see a server's mistakes as they were sent instead of after a validating model has filled in defaults or rejected the payload outright. The trade-off is that rules re-implement a little shape-checking the SDK would otherwise do for free (every rule must tolerate a missing or wrongly typed field), and checks that need behaviour rather than shape, like whether a tool actually responds, cannot live in the static engine; those run in the separate, opt-in `--smoke` phase and report through declared X-series rules so they still share IDs, severities, and `--ignore`.
